# 4 septembre 2026, session D : LS-178, cinq hypothèses fausses et un débit disque

Close sur constat. `npm ci` variait d'un facteur trente, la cause est **externe**
et ne se corrige pas ici. Le dernier critère de la story prévoyait ce cas.

## Ce qui a tranché : les horodatages

| Moment | Événement |
| --- | --- |
| 09:39:22 | l'étape démarre |
| 09:39:36 | les trois scripts d'installation, **moins d'une seconde chacun** |
| 09:39:36 à 09:46:25 | **6 min 49 de silence complet** |
| 09:46:25 | « added 704 packages in 7m » |

Ce silence est l'écriture de `node_modules` sur disque : **1,3 Go pour 704
paquets, environ 3,2 Mo/s**. Un débit anormalement bas, qui varie d'un exécuteur
GitHub à l'autre.

**Cela explique enfin pourquoi aucun critère du dépôt ne séparait les neuf
mesures**, 14 à 431 s : la cause n'est pas dans le dépôt.

## Cinq hypothèses posées et démenties

| Hypothèse | Verdict |
| --- | --- |
| Le cache npm ne se sauvegarde pas | faux, « Cache restored successfully » |
| Le motif est binaire, 17 s ou 425 s | faux, mesures à 216 et 217 s |
| `node_modules` est déjà présent sur les runs rapides | faux, 0 entrée avant, 498 après |
| Les scripts d'installation sont coûteux | faux, moins d'une seconde chacun |
| Le cache Prisma corrige le problème | faux, 423 s avec contre 425 s sans |

Toutes sont écrites dans `controles.yml`, pour qu'on n'y revienne pas.

## Le motif qui dépasse ce ticket

**Voir une chose au bon endroit ne prouve pas qu'elle consomme le temps.**
`--foreground-scripts` a rendu trois scripts visibles, et leur seule visibilité a
suffi à les faire accuser. Le journal les montrait juste avant sept minutes de
silence, ce qui ressemblait à une preuve. Ce sont les horodatages qui ont dit
qu'ils s'exécutaient en moins d'une seconde.

**Une mesure a aussi été faussée par une course.** Un cache créé sur
`refs/pull/226/merge` n'est pas visible depuis `main` : le nocturne a démarré
cinquante secondes avant que le cache de `main` n'existe, et un cache absent a
été lu comme un cache inefficace. Le troisième relevé, cache réellement
restauré, a donné 423 s contre 425 s sans.

## Ce qui est gardé, et pourquoi

**Le cache des moteurs Prisma.** Il ne résout pas LS-178, et les deux workflows le
disent. Il coûte zéro et supprime un téléchargement de 8 Mo, mesuré : le
`preinstall` de `prisma` disparaît du journal quand il est restauré.

**`--foreground-scripts`.** Coût nul, et il rendra visible le jour où une
dépendance ajoutera un script d'installation réellement coûteux.

Les relevés d'instrumentation sont retirés, la cause étant établie.

## Ce qui n'est pas fait

**1,3 Go de dépendances est normal** pour Next.js 16, Prisma et Playwright
réunis, et l'exécuteur GitHub ne se choisit pas. Réduire l'arbre de dépendances
serait un autre sujet, avec un autre arbitrage.

Le critère « la chaîne ne dépend plus du registre pour une installation
identique » n'est pas rempli : elle n'en dépendait déjà pas, le cache npm
fonctionnant. Ce critère visait une cause qui n'était pas la bonne.
